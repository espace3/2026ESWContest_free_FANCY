## 왜 이 문제가 구조적으로 존재하는가

Pi 5는 pigpio(DMA 기반 하드웨어 타이밍)를 쓸 수 없어 lgpio만 선택지인데, lgpio의
`tx_pwm`은 **소프트웨어 타이밍**이다. 즉 펄스 간격을 커널 스케줄러에 의존하는 스레드가
만들어낸다. 그 스레드가 선점당하면 스텝 펄스 간격이 불규칙해지고, 로터가 그 지터를
따라 덜컹거린다. 심하면 스텝을 잃는다(탈조).

추적 중에는 한 프로세스에 스레드가 22개(TFLite 3 + 메인 루프 + 카메라 리더 + lgpio +
…)인데 코어는 4개다. 초과 구독 상태라 펄스 스레드가 쉽게 밀린다.

### 증상

달그락거리는 소리가 난다. `tools/drive_motor.py` 단독 구동은 어떤 조건(긴 이동/왕복/잔이동/

lgpio의 펄스 생성 스레드가 일반 우선순위(SCHED_OTHER)로 돌아서, CPU가 초과 구독되면
선점당해 스텝 펄스 간격이 흔들린다.

## 재는 법 (대책을 고르기 전에 숫자부터)

귀로 "조용/시끄러움"만 비교하면 대책 다섯 개 중 뭐가 들었는지 못 가른다. 두 가지를
만들어뒀다.

**① 실측 — `--timing` (권장).** 진짜 시스템에서 직접 잰다. 배선 불필요.
`_sched_end`가 이미 "큐에 넣은 펄스가 다 나갈 예정 시각"을 들고 있으므로 실제 완료
시각과 비교하면 된다 (`motor_controller._Axis._execute`).

    계획   = Σ(청크 스텝수 / 주파수)      실측 = 첫 청크 큐잉 ~ 마지막 펄스 송출 완료
    드리프트 = 실측 - 계획 > 0  →  펄스 열이 늘어졌다 = 펄스 스레드가 선점당했다
    언더런  = 앞 청크가 다 나간 뒤에야 다음 청크를 넣은 횟수 (= 펄스가 실제로 끊김)

```bash
python tools/drive_motor.py --sweep 60 --cycles 3 --timing   # 부하 없는 기준선
python main.py --axis pantilt --timing     # 소리 나는 그 조건
python main.py --axis pantilt --timing --no-rt --no-pin  # 대책 끄고 비교
```

**② 대리 측정 — `tools/measure_jitter.py`.** 모터·배선 없이 "스레드가 예정보다
얼마나 늦게 깨는가"만 잰다. 대책 후보를 코드에 넣기 전에 A/B 하는 용도.

## 실측값 (2026-08-07, Pi 5 4코어, f_max 6000 → 에지 간격 T=83.3us)

`tools/measure_jitter.py`, 부하는 busy loop 6개. "초과분"은 바닥(sleep 오버헤드)을 뺀 값:

| 조건 | 바닥 | p90 | p99 | max | T 초과 |
|---|---|---|---|---|---|
| 무부하 | 52.7us | 2.4 | 3.2 | 442.9 | 0.01% |
| 부하 6 | 54.2us | 17.9 | 33.8 | 522.7 | 0.04% |
| `chrt -f 10` + 부하 6 | 5.8us | 10.9 | 16.3 | **46.2** | **0%** |
| 슬랙 1ns + 부하 6 | 4.3us | 17.3 | 32.4 | 672.3 | 0.03% |

→ **슬랙은 바닥만 낮추고 꼬리를 못 건드린다. RT는 둘 다 잡는다.** max 522→46us가
결정적이다.

`--timing` 드리프트(실모터, 추적 중):

| 상태 | 드리프트 |
|---|---|
| 대책 없음 | 3~7% |
| 어피니티만 | ~1%, 가끔 3% |
| 어피니티 + RT | 그보다 낮음, 소리 거의 사라짐 |

언더런은 어느 조건에서도 0이었다 — **큐가 비는 게 아니라 펄스 스레드 자체가 느려진
것**이라는 최종 확인이다.

## 적용된 대책 (`motor_controller.open_chip()`)

스레드는 **만든 쪽의 어피니티 마스크와 스케줄링 정책을 물려받는다** (glibc의
`pthread_create` 기본값이 `PTHREAD_INHERIT_SCHED`). 이 상속을 쓰면 tid를 알아낼 필요도,
`/proc/self/task` 차집합으로 스레드를 특정할 필요도 없다:

```
① 호출 스레드 → 펄스 코어 하나(마지막 코어) + SCHED_FIFO(prio 10)
② gpiochip_open()            ← lgpio 펄스 스레드가 둘 다 상속
③ 호출 스레드 → SCHED_OTHER + 나머지 코어(계산용)로 복구   ★ 필수
④ 이미 떠 있던 스레드(TFLite 등)도 계산 코어로 몰아냄
```

- **③이 필수인 이유**: 복구를 빠뜨리면 그 뒤에 만들어지는 워커·저장 스레드까지 RT가
  된다. 저장 스레드는 fsync를 하므로 RT로 돌면 위험하다. `finally`로 무조건 복구한다.
- **④가 필요한 이유**: 스크립트들이 모터보다 detector를 먼저 만든다. 사후에 옮겨주면
  스크립트 순서를 안 고쳐도 된다.
- RT는 `rtprio` 권한이 필요하다. 없으면 경고만 찍고 어피니티만 적용한다(죽지 않는다).
- 끄는 법: `--no-pin` / `--no-rt` (효과 비교용). 판정은 `--timing` 드리프트로.

### 적용 확인법

시작할 때 찍히는 줄:

```
[motor] 펄스 스레드 → 코어 [3] 전용, 계산 스레드 22개 → 코어 [0, 1, 2] | lgpio 신규 스레드 2개, 그중 RT 2개
```

- **신규 스레드 2개가 정상.** lgpio는 핸들 하나당 펄스 생성 + 알림 스레드를 만든다.
  둘 다 계산을 안 하고 자므로 RT여도 안전하다.
- **0개로 나오면 상속이 안 먹은 것** — lgpio가 스레드를 `gpiochip_open()` 때가 아니라
  첫 `tx_pwm()` 때 만든다는 뜻이고, 그러면 워커 스레드 쪽에 걸어야 한다.

실행 중 확인 (`-e`를 붙이면 시스템 전체가 나오니 주의):

```bash
ps -eLo pid,tid,cls,rtprio,psr,comm | awk 'NR==1 || $3!="TS"'   # RT 스레드만
ps -L -o psr= -p $(pgrep -f main.py) | sort | uniq -c  # 코어 분포
```

**FF가 정확히 2개**여야 한다. 5개 이상이면 ③ 복구가 실패한 것이다(워커·저장까지 RT).

### ⚠ 절대 하지 말 것

추적 스크립트 **전체**를 `chrt -f`로 실행하지 말 것. TFLite의 CPU 바운드 스레드가 RT로
돌면 커널 작업까지 밀어내 Pi가 멈출 수 있다. RT는 **계산을 하지 않는 펄스 스레드에만**
줘야 한다 — 위 ③이 그것을 보장한다. 실험에서 `chrt`를 쓴 것은 스레드가 적고 CPU를 안
먹는 `tools/drive_motor.py`/`tools/measure_jitter.py` 단독이었기 때문에 안전했다.

## 채택하지 않은 대안 (되살릴 필요가 생기면)

| 방향 | 왜 안 썼나 |
|---|---|
| lgpio 스레드를 `/proc/self/task` 차집합으로 특정해 승격 | 상속 트릭이 더 안전하고 짧다. 차집합은 창(window)에 다른 스레드가 끼면 **계산 스레드를 RT로 올려버린다** |
| 모터 제어 별도 프로세스 + RT | 작업량 큼(IPC·장부 소유권). 필요해지면 **`rgpiod` 데몬 + `rgpio` 클라이언트**가 지름길 — API가 거의 같고 데몬만 `chrt`로 띄우면 된다 |
| `--threads` 낮추기 | 근본 아님. 추론 FPS만 잃는다 |
| `f_max` 낮추기 | 속도를 잃는다. 같은 효과를 속도 손실 없이 얻으려면 **마이크로스텝 1/16→1/8** (같은 각속도에 펄스 주파수 절반). TODO의 틸트 속도 항목과 함께 볼 것 |
| 패치된 lgpio 재설치 | 절차 유실 + 효과가 검증된 적 없음 + venv마다 재적용. 폐기 |
