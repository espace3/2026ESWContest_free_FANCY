## 왜 이 문제가 구조적으로 존재하는가

Pi 5는 pigpio(DMA 기반 하드웨어 타이밍)를 쓸 수 없어 lgpio만 선택지인데, lgpio의
`tx_pwm`은 **소프트웨어 타이밍**이다. 즉 펄스 간격을 커널 스케줄러에 의존하는 스레드가
만들어낸다. 그 스레드가 선점당하면 스텝 펄스 간격이 불규칙해지고, 로터가 그 지터를
따라 덜컹거린다. 심하면 스텝을 잃는다(탈조).

추적 중에는 한 프로세스에 스레드가 22개(TFLite 3 + 메인 루프 + 카메라 리더 + lgpio +
…)인데 코어는 4개다. 초과 구독 상태라 펄스 스레드가 쉽게 밀린다.

## 2026-08-07 진단

### 증상

카메라 추적(`verify_track_*`, `verify_fulltrack`, `verify_E2E_v1`)을 돌리면 모터에서
달그락거리는 소리가 난다. `verify_motor.py` 단독 구동은 어떤 조건(긴 이동/왕복/잔이동/
넓은 범위)에서도 조용하다. 소리는 **모터가 실제로 도는 동안에만** 난다.

### 원인

lgpio의 펄스 생성 스레드가 일반 우선순위(SCHED_OTHER)로 돌아서, CPU가 초과 구독되면
선점당해 스텝 펄스 간격이 흔들린다.

### 결정적 실험 (이 순서로 재현 가능)

| 조건 | 결과 |
|---|---|
| busy loop 3개(코어 1개 여유) + `verify_motor --sweep 60 --cycles 3` | 조용 |
| busy loop 6개(코어 초과 구독) + 같은 명령 | **소리** |
| busy loop 6개 + `sudo chrt -f 10 $(which python3) …`로 같은 명령 | **조용** ← 확정 |
| 추적 중 `--threads 3 → 1` | 소리 줄어듦 |

```bash
# 부하 만들기 / 없애기
```

## 해결 방향과 장단점 (2026-08-07 기준 미적용)

| 방향 | 장점 | 단점 |
|---|---|---|
| **A. lgpio 스레드만 골라 RT로 승격** (권장) | 원인을 정확히 겨냥. 코드 20줄 남짓, `motor_controller.py` 안에서 끝남. 구조 변경 없음. TFLite는 일반 우선순위 유지 | `/etc/security/limits.conf`에 `rtprio` 허용 필요(또는 sudo). `gpiochip_open()` 전후 `/proc/self/task` 차집합으로 스레드를 특정하는 방식이라 lgpio 내부 구현에 의존 |
| **B. 모터 제어를 별도 프로세스로 분리 후 그 프로세스만 RT** | CLAUDE.md 동시성 방침에 맞는 정석. 모터 프로세스는 계산이 거의 없어 RT여도 안전. BLE·릴레이까지 붙었을 때 확장성 좋음 | 프로세스 간 통신(목표각 전달, 현재 위치 조회) 신설 필요. 위치 저장 소유권 정리 필요. 작업량 큼 |
| **C. `--threads` 낮추기** | 인자 하나. 즉시 효과 확인됨 | 추론 FPS 하락 (3스레드에서 21.9fps 측정 — 목표 20fps를 못 지킬 수 있음) |
| **D. `f_max` 낮추기** | config 한 줄 | 팬이 이미 6.75°/s(f_max 6000)라 빠듯하다. 절반이면 응답 0.5s 내 이동량이 3.4° → 1.7°. TODO.md "틸트 최고 속도 부족" 항목과 정면 충돌 |
| **E. 패치된 lgpio를 venv에 재설치** | 근본 해결. A/B 없이도 풀릴 수 있음 | 절차 문서가 유실돼 복원 필요. venv를 새로 만들 때마다 재적용해야 함 |

### ⚠ 절대 하지 말 것

추적 스크립트 **전체**를 `chrt -f`로 실행하지 말 것. TFLite의 CPU 바운드 스레드가 RT로
돌면 커널 작업까지 밀어내 Pi가 멈출 수 있다. RT는 **계산을 하지 않는 펄스 스레드/
프로세스에만** 줘야 한다. 위 실험에서 `chrt`를 쓴 것은 스레드가 적고 CPU를 안 먹는
`verify_motor.py` 단독이었기 때문에 안전했다.
